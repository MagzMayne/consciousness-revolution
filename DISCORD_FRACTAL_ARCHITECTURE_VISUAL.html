⚡ Template + Config Pattern (THE BREAKTHROUGH)

The Problem

CURRENT CHAOS: User 1 edits: COMMANDER_COCKPIT.html User 2 edits: COMMANDER_COCKPIT.html User 3 edits: COMMANDER_COCKPIT.html Git: "WTF do I merge? 🔥💀🔥" Result: Lost changes, conflicts, pain

The Solution

TEMPLATE + CONFIG ORDER: ONE template: COCKPIT_LAUNCHER.html (read-only, version controlled) User 1 config: { widgets: [A, B, C], theme: "dark" } User 2 config: { widgets: [A, D, E], theme: "light" } User 3 config: { widgets: [B, C, F], theme: "dark" } Git: "No conflicts! All configs in database! ✅" Result: Zero merge conflicts, infinite customization

How It Works (Runtime Flow)

Step 1: User Loads Page

User navigates to: consciousnessrevolution.io/cockpit

Step 2: Detect User

JavaScript: const user = await getCurrentUser();

Step 3: Load Config from API

GET /.netlify/functions/dashboard-config?user_id={id}

Returns: JSON config from Supabase

Step 4: Apply Config to Template

JavaScript: applyConfig(config)

  • Show/hide widgets based on config.widgets
  • Apply theme CSS variables
  • Set layout mode (personal/team/commander)
  • Load personal files (avatar, background)
Step 5: Render Unique Dashboard

Result: Same template, completely different dashboard per user

Config Structure (JSON Schema)

{ "user_id": "uuid-tiger", "dashboard_template": "COCKPIT_LAUNCHER", "variant_name": "Tiger's Custom Cockpit", "layout": { "grid": "7+1", "view_mode": "personal", "default_domain": "1_COMMAND" }, "widgets": [ { "id": "feat_xp_tracker", "enabled": true, "position": { "quadrant": "top-right", "order": 1 }, "config": { "show_level": true } }, { "id": "feat_task_list", "enabled": true, "position": { "quadrant": "top-left", "order": 1 }, "config": { "filter": "assigned_to_me" } } ], "theme": { "primary_color": "#667eea", "bg_color": "#0a0a0f" }, "personal_files": [ { "type": "avatar", "path": "users/tiger/avatar.png" } ], "access_level": "operator", "favorites": ["BRAIN_QUERY_DASHBOARD"] }

Migration Process (Per Cockpit)

STEP 1: Extract Config
  • Read existing HTML file
  • Identify: Layout, Widgets, CSS, Personal content
  • Generate config JSON
STEP 2: Validate Against Base Template
  • Can base template render this config?
  • Identify gaps (missing widget types, unsupported layouts)
  • Document gaps for template enhancement
STEP 3: Create Variant Record
  • Insert into dashboard_variants table
  • Store config JSON
  • Mark status as "migrated"
STEP 4: Test Render
  • Load template + config
  • Compare visual output to original
  • Get user approval
STEP 5: Deprecate Old File
  • Rename: .html → .legacy.html
  • Add redirect to new launcher
  • Keep legacy for 30 days, then delete

Version history snapshots

Widget library registry

Pinned dashboards
